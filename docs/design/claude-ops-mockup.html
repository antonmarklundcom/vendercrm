Notes on the concept

Why the page is shaped this way, for whoever builds it.

  1. 01

    One page, one batch at a time

    The owner works in bursts of five to ten domains. A batch is the unit of work: it holds the raw text, the rows the session derived from it, the token that was allowed to act on it, and the log slice. Past batches are one click away and stay readable forever.

  2. 02

    Raw text is the source, the table is the interpretation

    The paste box stores exactly what the owner wrote. The session reads it through the ops API and writes back one row per domain. The table exists so the human can spot a misread before anything is provisioned, and again before anything goes live.

  3. 03

    Five steps, one strip

    Company, site, pipeline, key, test lead. The strip encodes state in form, so a scan of the column tells the owner where the batch is without reading a word. A failed cell carries the API's own reason, verbatim, because a paraphrased error is worth less than a real one.

  4. 04

    Sites are born inactive

    The session can create everything but cannot activate. Approval is a human click on this page. It also deletes the test lead. That single gate is what turns "Claude did fifty things" into "Claude did fifty things and I checked each one in ten seconds".

  5. 05

    The token is scoped, bound, short-lived, and shown once

    It is bound to one batch, expires in hours, and cannot read existing keys or delete. After issue the page shows only the prefix, last use, and call count, the same treatment the codebase already gives site API keys. Revoke is always one click.

  6. 06

    The log is the existing audit log, filtered

    Every ops call writes a normal audit entry with the superadmin as actor and the token as the "via", mirroring how impersonation is already recorded. Nothing about this page needs a second trail.
