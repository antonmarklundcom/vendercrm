Sonnet, wave 2 lane 2, phase 1 of the sequential `sonnet-wave2-lane2.md` run.
Branch `phase/p13` off `main` at `3323402` (the wave 2 planning merge, #105).

## Built

- **Schema** (`src/db/schema/contracts.ts`, migration 0035): `contract_templates`
  (tenant, name, plain-text body, is_active), `contracts` (template snapshot,
  contact/deal?/quote?, `CON-` number, rendered body, status
  draft|sent|accepted|declined|voided, public token, pdf/signed-pdf storage
  keys), `contract_acceptances` (unique on contract_id, name typed, decision,
  IP, user agent, PDF SHA-256, an unused `signature_storage_key` for a later
  drawn-signature follow-up).
- **Rendering** (`modules/contracts/render.ts`, pure, unit-tested): `#`
  headings, blank-line paragraphs, `{{contacto.nombre|telefono|email}}` and
  `{{contacto.custom.<key>}}` variables; `negocio.*` refused until K3.
  Template save refuses an unknown variable, naming it.
- **Lifecycle** (`modules/contracts/contracts.ts`): create (renders against
  the contact) → send (freezes the body, stores the PDF, delivers by
  WhatsApp/email, `CON-` number via `document_sequences`) → the public page
  `/c/[token]` (rate-limited, same model as `/q/`) → click-to-accept/decline
  records the SHA-256 of the exact PDF bytes shown, re-renders a second PDF
  with an appended acceptance page under `signed_pdf_storage_key`, emits
  `contract.accepted` → the `contract_accepted` trigger P1 left unemitted.
  Void is admin-only + audited; a voided token stops resolving.
- **UI**: `/contracts` list + create, `/contracts/templates` editor (seeds
  three vertical presets on first visit), `/contracts/[id]` detail
  (send/void/email/copy-link), a "Contratos" tab on `contacts/[id]`, a
  "generar contrato" link on the deal and quote detail pages.
- **Tests**: `render.test.ts` (headings/paragraphs/variables/unknown
  refused); `contracts.integration.test.ts` (full lifecycle, PDF-hash
  evidence, trigger fires with the deal id, second decision refused,
  draft/unknown-token refusals, void stops resolving, cross-tenant
  isolation).

## Decisions and deviations

1. **`public_token` is stored in plaintext, not hashed.** The §17.3 phrasing
   ("public_token hash") is ambiguous, and a hashed value can't be
   redisplayed on the detail page's "copiar enlace" the way every sibling
   document (quote, nota de venta, receipt) already works — so this follows
   their existing plaintext model instead, minted once at creation and
   reused (not rotated) at send.
2. **The variable registry lives in `modules/contracts/render.ts`, not
   `automations/actions.ts`'s `renderTemplateVars`.** That function's
   namespace is English (`contact.name`/`contact.phone`); this phase's spec
   asks for the Spanish `contacto.*` namespace P5's (unwired)
   `renderContactCustomVars` already established for custom fields, so
   contracts gets its own small resolver rather than forcing a rename on a
   function three other phases already call.
3. **`generateContractPdf` renders fresh from the stored body** rather than
   serving the stored PDF — same "render is cheap, the stored copy can lag"
   rule the quote/document/receipt PDF routes already follow. The acceptance
   PDF is the one exception: it's rendered once, at decision time, and its
   bytes are exactly what the stored SHA-256 attests to.
4. **`contract_sent`/`contract_accepted`/`contract_declined` are generic
   `system` activities** with `payload.kind`, the same escape hatch P1/P4/P6
   used — `crm/activities.ts`'s `ActivityType` enum is outside this phase's
   Owns column.
5. **Templates are tenant-admin only** (`createContractTemplate` /
   `updateContractTemplate` via `requireTenantAdmin()`); creating and
   sending a contract itself is any agent's action, same split as quotes.

## Known issues

- `negocio.*` variables are not resolvable yet — a template referencing one
  is refused at save with the variable's name; K3 (later in this lane) is
  expected to add the registry entries.
- No drawn-signature pad — `contract_acceptances.signature_storage_key`
  exists and nothing writes to it; click-to-accept is the whole flow per
  §17.1 #5.
- `sendContractByEmailAction` does not flip contract status or write its own
  timeline activity distinctly from the WhatsApp send — same "does not touch
  quotes.status" precedent P4's `sendQuoteByEmailAction` set for quotes.
