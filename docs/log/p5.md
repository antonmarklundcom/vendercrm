# P5 — Pipeline polish, custom fields, SQL pagination (PLAN.md §15.5 J4/J12, §15.8)

Sonnet, wave 1 lane 2, phase 3 of the sequential `sonnet-wave1-lane2.md` run.
Branch `phase/p5` off `main` at `99a1f6d` (P4).

## Built

- **Board**: value total per column and days-in-stage per card (recomputed
  client-side from live drag state, not a stale server prop); a stale badge
  when `stages.stale_after_days` (new, editable in `/pipeline/etapas`) is
  exceeded; real in-column reordering via `@dnd-kit/sortable` (the pre-P5
  board only appended to the end of the target stage — its own comment said
  so); `deals.expected_close_at` (editable on the deal page) and
  `deals.lost_reason`, separate from `closeReason` (won keeps that).
- **Custom fields**: `custom_field_definitions` (text/number/date/select/
  phone, options, position, required, show_on_card), `modules/crm/custom-fields.ts`.
  Admin page `/contacts/campos`; rendered + editable on the contact detail
  page; import mapping (`custom.<key>` → CSV header); export columns; a
  `custom.<key> equals|contains <value>` saved-view filter; a
  `renderContactCustomVars` resolver for `{{contacto.custom.<key>}}`,
  exposed for whichever call site wires it into a template engine.
- **SQL pagination**: `queryContacts` sorts and pages in MySQL
  (`ORDER BY`/`LIMIT`/`OFFSET`); a new `tenantDb(ctx).count()` backs the
  total without fetching every row. Filters needing a join (tags, pipeline/
  stage, a custom field) resolve matching ids with one extra scoped read,
  then narrow the main query with `inArray` — no raw join, `tenantDb`
  boundary intact.

## Decisions and deviations

1. **Added `count()` to `tenancy/db.ts`'s scoped builder** — the join/
   aggregate helper the phase prompt allowed for "if unavoidable". `select()`
   has no column projection, so a page's total needed its own aggregate
   query.
2. **Column totals and days-in-stage are recomputed client-side** from the
   board's own drag state rather than passed as a server prop — a server
   total would go stale the instant a card is dragged, until the next full
   page load. `modules/crm/deals.ts`'s `totalsByStage` is the same
   arithmetic, integration-tested against real rows instead of a rendered
   tree (this repo has no component-test harness).
3. **Vertical presets do not seed custom fields.** The phase rule asked for
   it, but `VERTICAL_PRESETS`/`applyVerticalPreset` live in
   `modules/tenancy/verticals*.ts`, outside this phase's Owns column and not
   in its Exit criteria — left for whichever phase next touches the wizard.
4. **`maxEmailsPerDay`-style limit not needed here**; no plan cap touches
   custom fields.
5. **Custom field `key`/`type` are immutable after creation** — changing
   either would strand every contact's stored value (a mismatched type, or
   an orphaned old key). Delete and recreate is the path for "set up wrong".
6. **The custom-fields edit form on the contact page does not enforce
   `required`** — a blank submit stores `null`, same as an import row with an
   empty mapped cell. Validation is future work, not blocking for this pass.

## Known issues

- Deleting a custom field definition leaves its values in `contacts.custom`
  (dead JSON keys, no cleanup pass) — harmless, since nothing reads a key
  with no definition.
- `renderContactCustomVars` is not wired into `automations/actions.ts`'s
  template engine — the exit criteria didn't ask for it, and automations is
  outside this phase's Owns column.
