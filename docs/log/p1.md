# P1 — Automation library, trigger labels, notification rows (PLAN.md §15.5 J1, §15.8)

Opus, wave 1 lane 1. Branch `claude/opus-k1-business-memory-g41xpi` (this
session's designated branch; the phase prompt's `phase/p1` name is the only
deviation from §15.8's mechanics).

## Built

- **Triggers**: `quote_sent`, `quote_accepted`, `document_sent`,
  `document_paid`, `deal_won`, `deal_lost`, `contract_accepted` in
  `TRIGGER_TYPES`, the `flows.trigger_type` drizzle enum and all three
  locales. New event buses `modules/quotes/events.ts` and
  `modules/documents/events.ts`, emitted from `sendQuote`,
  `sendDocumentToContact` and `recordPayment`, listened to in
  `automations/triggers.ts`.
- **Labels**: the five triggers §15.0 #4 found unlabelled
  (`booking_created/cancelled/no_show/completed`, `chat_lead_captured`) plus
  `offer_slots`, which was missing from the palette too.
- **Actions**: `create_task`, `notify_user`, `send_email` — all three reach a
  person on the team rather than the customer, all three degrade to a skipped
  step with a reason when unconfigured.
- **Conditions**: `deal_value` (gte/lt), `lead_source`, `site`,
  `contact_field` (reads `contacts.custom`, whose UI lands in P5).
- **Notifications**: `notifications` table (migration 0029),
  `modules/notifications/`, and a bell in the app nav header showing the ten
  most recent with an unread count and "mark all read".
- **Run detail**: `/automations/[id]/runs/[runId]` renders `flow_run_steps`
  with the raw result JSON; the runs table links to it.
- **Parity test**: `src/i18n/messages.test.ts` now imports `TRIGGER_TYPES`,
  `CONDITION_KINDS` and `ACTION_KINDS` and fails when any of them ships
  without a label in es/en/sv.

## Decisions and deviations

1. **`deal_won`/`deal_lost` are derived from `deal.stage_changed`**, not
   emitted from `closeDeal` as the prompt sketched. The stage flags
   (`stages.is_won/is_lost`) are what "won" means in this product, so a card
   dragged into Ganado on the board now fires the same trigger as the close
   button — one listener instead of two emit sites that can drift. It also
   keeps P1 out of `modules/crm/deals.ts`, which P5 owns.
2. **`modules/notifications/` is created here**, though §15.8 lists it under
   P2. P2 adds push delivery on top of these rows; the row has to exist
   first, and lane 1 is sequential so there is no concurrent writer.
3. **The bell is wired in `(app)/layout.tsx`** — three lines in a file the P8
   link pass also touches. Unavoidable: the prompt asks for the bell in the
   nav header, and the header is composed there.
4. **`send_email` calls `lib/email`'s `sendEmail` unchanged.** P4 gives
   tenants their own sending identity behind the same function, so this
   action inherits it without being rewritten.
5. **`document_paid` fires once**, decided by comparing the ledger before and
   after the insert inside `recordPayment` — a second instalment on an
   already-settled document emits nothing.
6. `create_task` and `notify_user` resolve the assignee from the record
   (`deal_owner` → `contact_owner` → a specific id), so reassigning a deal
   keeps sending tasks to the right person.

## Known issues

- `quote_accepted` (P6) and `contract_accepted` (J5) have no emitter yet, so
  a flow built on them today never fires. Deliberate — the enum entry is what
  those phases need not to add.
- `countUnread` counts rows in Node rather than with `count(*)`; fine at the
  bell's scale, worth folding into P2's notification queries if that changes.
- The `notify_user` row always links to `/contacts/<id>`; a deal- or
  document-aware URL is P2's to refine when push carries the same payload.
