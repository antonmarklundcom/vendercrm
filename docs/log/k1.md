# K1 — Business memory (PLAN.md §16.1–§16.4)

Opus, wave K lane 1. Branch `claude/opus-k1-business-memory-g41xpi`.

## What now exists

- **Schema (`src/db/schema/memory.ts`, migration `0028_add_business_memory`)** —
  `business_profiles`, `business_facts`, `memory_imports`, `setup_plans`, all four
  created now so K2 and K3 add no migrations (§16.6). The FULLTEXT index on
  `business_facts(title, body)` is hand-written in the migration: drizzle-kit's
  MySQL dialect cannot express one, so **do not regenerate 0028** from the schema
  without re-appending it (and the data copy below).
- **The data copy** — the migration copies `settings.ai.businessName/about/tone/
  neverPromise` into `business_profiles` and the free-text `settings.ai.hours`
  into a confirmed `location` fact titled "Horario" (§16.3). The old keys stay
  readable for one release: `modules/memory/checklist.ts`'s
  `profileFromLegacyAiSettings` is the same mapping in code, used by
  `buildMemoryContext` for a tenant that has no profile row yet, and unit-tested
  as the statement of what the SQL does.
- **`src/modules/memory/`** — `profile.ts` (get/upsert, `refreshCompletedPct`),
  `checklist.ts` (pure: the eight checklist rows, `completedPct`, the legacy
  copy), `facts.ts` (CRUD/confirm/list, per-kind `structured` zod, visibility and
  confirmation enforced as WHERE clauses), `retrieve.ts`
  (`buildMemoryContext(ctx, {query, budgetTokens, audience})` — profile + hours +
  policies always, top-k FAQs/services by `MATCH … AGAINST`, promos in date),
  `pack.ts` (pure budget packing, deterministic order), `render.ts` (the Spanish
  voseo prompt block, `formatBusinessHours`, `formatGs`).
- **`lib/ai`** — `generateStructured` is now part of the driver interface, with
  JSON mode on OpenAI (`response_format: json_schema`, non-strict) and Gemini
  (`responseMimeType` + a pruned `responseSchema`); `structured.ts` holds the
  provider-neutral zod validation and the single retry with the validation error
  appended. `buildSystemPrompt` takes the rendered memory block instead of the
  four free-text fields; `BusinessContext.neverPromise` stays because the chat
  widget overrides it per widget.
- **Ledger** — `ai_replies.kind` (`reply | memory_extract | setup_plan`, defaulted
  to `reply`) so K2/K3's structured calls are audited and capped through the same
  table and the same per-tenant daily ceiling (§16.2 rule 6).
- **`/settings/negocio`** — admin-only profile form, facts grouped by kind with
  add/edit/confirm/delete, the completion checklist, internal facts badged in the
  list. Confirm/edit/delete/profile writes go through `writeAuditLog`
  (`memory.fact_confirmed`, `memory.fact_updated`, `memory.fact_deleted`,
  `memory.fact_created`, `memory.profile_updated`). Keys under `app.memory` in
  `messages/es|en|sv.json`.

## Decisions worth knowing

1. **The pure/DB split.** `checklist.ts` and `pack.ts` exist because the repo's
   test bar is that decisions are unit-testable without MySQL (the
   `modules/booking/slots.ts` pattern). The queries stay in `profile.ts` and
   `retrieve.ts`.
2. **Retrieval degrades, never throws.** A `MATCH … AGAINST` against a database
   without the FULLTEXT index is caught and falls back to a LIKE scan on the
   longest words, so a hand-migrated deployment answers worse rather than not at
   all.
3. **The free-text "Horario" fact beats the structured week** when both exist: a
   business that wrote a sentence said something the seven-row form cannot.
4. **Budget order is the spec.** Profile, hours and the always-facts (policy,
   location, contact) are never dropped; retrieved facts fill what is left,
   best-first, then promos. `truncated` says when something was cut.

5. **Promo dates are the tenant's dates.** The pre-handoff audit found
   `isPromoActive` comparing UTC's today, which drops a "hasta el 30" promo at
   21:00 on the 30th in Asunción; it now takes the tenant timezone
   (`todayIn`), fixed in the follow-up commit.

  writing `settings.ai`. Those fields are now inert for a tenant that has a
  profile row — the memory wins. The P-wave owns that file; the link pass should

- `memory_imports` and `setup_plans` are created and unused until K3/K2.
- DB-backed suites (`memory.integration.test.ts`) cannot run in the build
  container — no MySQL — so they were verified in CI, not locally.
