## Built

- **`reports/sales.ts` grows**: `getSalesReport(ctx, window, filters?)` takes
  an optional `{pipelineId?, agentUserId?}` that narrows every table by
  filtering the one `dealRows` array everything downstream already reads.
  `AgentRow` gains `leads`, `dealsOpened`, `dealsLost`,
  `responseMedianMinutes` (per-agent median first-response, attributed by
  who actually sent the reply). New: `previousWindow` (same length,
  immediately before), `computeResponseBuckets` (answered conversations in
  four fixed buckets: <15m, 15m-1h, 1h-24h, >24h), `computeStageFunnel`
  (cumulative "reached this stage or further" per pipeline, read off each
  deal's *current* stage — no stage-history table exists to ask "did it
  ever pass through"). `firstResponsesByConversation` is the one shared pass
  `computeResponseTimes`/`computeResponseBuckets`/per-agent medians are all
  built from, so "who replied" and "how long" never drift apart.
- **`reports/compare.ts`** (pure): `withComparison` attaches the previous
  window's same metric to each row of a keyed table (sources, sites).
- **`/reports`**: a single GET filter form (date presets 7/30/90 + custom
  from/to, pipeline picker, agent picker — every value in the URL); funnel
  cards with a %-delta vs. the previous window; sortable tables (client-side
  — §10 1R #1's URL-state rule is about filters, not a throwaway sort click)
  for sources, sites, agents; the stage funnel (only when a pipeline is
  picked) and the response-time distribution.
- **`/api/exports/reports/[table]`**: `agents | sources | sites | stages |
  response`, session-guarded, rate-limited, reading the identical
  `parseReportsWindow`/`parseReportFilters` (`app/(app)/reports/query.ts`)
  the page uses — the same URL always means the same rows.
- **Campaigns table omitted** — `campaign_recipients` doesn't exist on
  `main` yet (P10, lane 1, not merged when this phase ran); the phase rule's
  fallback ("otherwise omit and log") applies.

## Decisions and deviations

1. **Sort is client-side, not URL state.** §10 1R #1 exists so a *filter*
   round-trips through a bookmark or the back button; which column a rep
   last clicked to re-sort a report table by is throwaway UI state with no
   sharing value, so `SortableTable` keeps it in `useState` rather than the
   URL — the filters (date range, pipeline, agent) are the part that's
   actually in the URL.
2. **Stage funnel is current-state, not historical.** "Stage-by-stage
   conversion" read literally (did a deal ever reach stage N, even if it's
   since moved on) would need every `stage_change` activity replayed per
   deal; this reads `deals.stage_id` directly and counts cumulatively by
   stage position instead — simpler, no schema change, and the number a
   rep actually wants ("how many are at or past proposal right now").
3. **The pipeline filter scopes literally everything** (funnel, sources,
   sites, agents, months) to that pipeline's deals, not just the stage
   funnel — a tenant with several pipelines (§10 1R #1) gets one coherent
   report per pipeline rather than a mix of scoped and unscoped numbers.
4. **The agent filter narrows deals, not messages.** `response`/
   `responseDistribution` stay tenant-wide even when an agent is picked —
   messages aren't owned by a deal's assignee, so filtering them the same
   way would misrepresent "how fast does this business answer" as "how fast
   does this rep reply," which `byAgent[].responseMedianMinutes` already
   answers correctly per row.

## Known issues

- No campaigns table yet — logged above, resolved automatically once P10
  merges and this phase (or a follow-up) adds the fourth table.
- `getSalesReport` runs twice per page load (current + previous window) —
  fine at today's per-tenant data volume; worth a single combined query if
  a tenant's deal count ever makes two full-table scans noticeable.
- The response-time distribution and stage funnel have no comparison column
  — only the keyed tables (sources, sites) do, since `withComparison` needs
  a stable key and a bucket's previous-window value isn't obviously more
  useful than its current one already being a distribution.
