# K2 — The AI setup assistant (PLAN.md §16.5, §17.2)

Sonnet, run directly in a Claude Code session (not the Opus lane the plan
names — see Decision 1 below), on top of `main` after #119 and #120 (P9)
had merged. Built out of order: the plan's lane-1 sequence is K2 → P9 → P10
→ P11, but the earlier session that produced #117/#118 started at P9
instead, so K2 was still outstanding when this session started (see
`KNOWN-ISSUES.md`'s K2/K3 entry).

## Built

- **Preset shape extensions** (`modules/tenancy/verticals.ts`, data only,
  §16.5's list): `PresetStage` (a plain string, unchanged, or
  `{name, isWon, isLost, staleAfterDays}`), `PresetFlow.trigger` widened to
  add `wa_message_received | lead_received | deal_won`, `PresetFlow.conditions
  ?: ["outside_business_hours"]`, `PresetQuickReply`, and `aiMode?: "draft"`
  on `VerticalPreset`. All six catalogue presets now carry 1-2 quick replies
  and `aiMode: "draft"`; their `pipelineStages` stay plain strings — only the
  setup assistant's generated plans use the object form.
- **`verticals-apply.ts`**: one apply step per new field — `applyQuickReplies`
  (idempotent by name, `modules/whatsapp/quick-replies.ts`), stage
  `isWon`/`isLost`/`staleAfterDays` passed through `createStage`, `applyAiMode`
  (`updateTenantAiSettings`, only when the tenant has never chosen a mode —
  never fights a later human choice). `graphFor` gained the
  `outside_business_hours` gate: a `business_hours` condition node, "no"
  branch, ahead of the wait/message pair — the manual flow editor's own
  condition kind, not a new one (K2's hard limit). Review-request flows now
  also fire on `deal_won`, not only `booking_completed`. `applyVerticalPreset`
  is now a catalogue-slug lookup in front of a new `applyPreset(ctx, preset)`,
  so the setup assistant's AI-generated preset goes through the exact same
  function (§16.2 rule 3) instead of a parallel apply path.
- **`crm/pipelines.ts`**: `createStage` takes `staleAfterDays` (the column
  already existed, from J4/P5; nothing else used it as an input yet).
- **Migration `0040_add_setup_conversation`**: one additive column,
  `setup_plans.conversation` (json) — the conversation's own progress
  (current topic index, answers, skips), separate from `brief` (the finished
  summary handed to `generateSetupPlan`) and `preset`/`outcome`. No new
  tables, per K2's hard limit (K1 already created `setup_plans`).
- **`modules/setup/`**:
  - `conversation.ts` — pure, import-free (K1's checklist.ts/narrative.ts
    pattern): the eight fixed topics (§16.5 step 2), `advanceConversation`
    (skip-or-answer, one topic at a time, a no-op on a stale/out-of-order
    post), `parseFaqBlocks` (blank-line-separated Q/A blocks, capped at 5),
    `matchTone`.
  - `schema.ts` — also pure: `SETUP_PLAN_SCHEMA` (the model's JSON-mode
    output — 5-7 stages with exactly one won and one lost, 3-5 quick
    replies, up to 4 booking types, an optional welcome and review-request
    message, `closestVerticalSlug`) and `presetFromOutput`, which clones the
    closest catalogue preset (§16.5 step 3: "may start from the closest
    catalogue preset and adapt") and overlays what the model generated.
  - `plan.ts` — the DB half: the one draft row per tenant
    (`getDraftSetupPlan`/`upsertSetupPlanConversation`), `buildSetupBrief`
    (profile + always/retrievable facts, §16.4's "everything" for the setup
    assistant), `generateSetupPlan` (one `driver.generateStructured` call,
    the tenant's daily cap, a ledger row on every attempt — `kind:
    "setup_plan"` already existed on `ai_replies` from K1), `applyAnswer` +
    `submitSetupAnswer` (writes the topic's answer into the memory as a
    confirmed fact or profile field, merging into the existing profile
    rather than replacing it — unlike the settings form, one topic writes
    one field at a time).
  - `apply.ts` — `applySetupPlan` (calls `applyPreset`, flips the plan to
    `applied`, `writeAuditLog`) and `discardSetupPlan` ("empezar de nuevo").
- **`/onboarding`**: assistant-first. A draft conversation renders the
  current topic (textarea + Continuar/Saltar); finishing it generates the
  plan immediately and shows the preview (stages, quick replies, flows) with
  Aplicar/Empezar de nuevo; a failed or unavailable generation says so and
  offers Reintentar. The manual picker moved under a `<details>` disclosure,
  "Elegir un rubro sin el asistente" — unchanged otherwise, `stageName()`
  handles the widened `pipelineStages` type.
- **Superadmin**: "Configurar con IA" next to "Ver como" on each admin row
  of the tenant detail page — the same `startImpersonation` swap, redirecting
  to `/onboarding` instead of `/dashboard`, so the guard, caps and audit
  trail are exactly the tenant's own (no separate code path).

## Decisions and deviations

1. **Built by a Sonnet session, not the Opus lane the plan names.** The
   owner asked directly whether K2/K3 could be done "here" — this session —
   rather than by spawning a separate Opus session per §17.2's lane
   assignment. Nothing in K2 needs Opus specifically; the model split in
   the plan was a cost/quality judgment call, not a technical requirement.
2. **Widget welcome copy — deferred, not built.** §16.5 lists `widget?:
   {welcome, captureAfterMessages}` among the shape extensions. Chat widgets
   (`chatWidgets` table) belong to a `siteId` — an embed on a specific
   website — which a fresh tenant going through the assistant does not
   necessarily have yet. Auto-creating a site to hang a widget off of is a
   bigger, unasked-for commitment than the additive/idempotent apply steps
   above; inventing one silently would also cut against "additive never
   invents infrastructure." Left for a phase that owns the chat-widget
   surface directly.
3. **No "no-reply follow-up after 2 days" flow.** §16.5 step 3 lists it
   among what a generated plan should include. There is no trigger for "N
   days since the last inbound message" in `automations/graph.ts`'s
   `TRIGGER_TYPES` — only event-driven triggers exist, no scheduled/elapsed-
   time one — and K2's hard limits forbid adding a new trigger type. The
   generated plan produces the other two flows §16.5 asks for (a welcome
   message gated on `outside_business_hours`, a review request on
   `deal_won`) and skips this one.
4. **One free-text answer per topic**, even where §16.5 groups two questions
   under one bullet ("horario y dirección", "señas/cancelación/pagos"): a
   single textarea per topic keeps `conversation.ts`'s state machine small
   and testable without a database, and a free-text answer is exactly what
   `generateSetupPlan`'s brief reads regardless. FAQs are the one topic that
   fans out (blank-line-separated blocks, capped at 5) because §16.5 asks
   for "the 5 questions" by name.
5. **The AI-generated plan's flows are limited to two fixed kinds**
   (welcome-outside-hours, review-on-won) rather than letting the model
   invent arbitrary trigger/text combinations. Validating an open-ended
   flow shape from a JSON-mode call would mean re-deriving the whole
   `FlowGraph` schema inside the setup assistant; two named slots
   (`welcomeMessage`/`reviewRequestMessage`, both optional) keep the model's
   output inside what `verticals-apply.ts` already knows how to build.
6. **`policies`' structured topic is always `"cancellation"`.** The
   `business_facts.structured` schema for a `policy` fact requires exactly
   one `topic` (`cancellation | deposit | payment | warranty | other`); the
   conversation's single "señas, cancelación y pagos" question covers three.
   `cancellation` is the closest single label; an admin can retag it from
   `/settings/negocio` afterwards.
7. **`contactToday`'s answer is stored `visibility: internal`** — "how do
   customers reach you today" is operational context for the assistant, not
   something that should ever render in a customer-facing prompt.

## Known issues

- **K3 can now be attempted** — it was skipped this wave because its own
  prompt hard-depends on K2 (`docs/log/p18.md`, `KNOWN-ISSUES.md`). K2 is
  merged as of this phase; K3 has not been run yet.
- **DB-backed suites** (`setup.integration.test.ts`,
  `verticals-apply.integration.test.ts`'s new case) **cannot run in this
  build container — no MySQL — so they were verified in CI, not locally**
  (same as K1). `conversation.test.ts` and `schema.test.ts` are pure and ran
  locally.
- **The retry button after a failed generation re-runs the same brief.** If
  the failure was the tenant's daily AI cap rather than a transient
  provider error, retrying immediately still fails; the message shown does
  not currently distinguish the two reasons on screen (both render the same
  `generationFailed` copy). `generateSetupPlan`'s typed reason
  (`ai_unavailable | daily_cap_reached | generation_failed`) is available to
  a future pass that wants to split the copy.
- **No manual "edit an answer" before the conversation ends** — "Empezar de
  nuevo" discards the whole draft rather than letting an admin go back one
  topic. Acceptable for a first pass since every answer is also visible and
  editable afterwards on `/settings/negocio`.
