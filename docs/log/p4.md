# P4 — Email identity and delivery surfaces (PLAN.md §15.1, §15.5 J3, §15.8)

Sonnet, wave 1 lane 2, phase 2 of the sequential `sonnet-wave1-lane2.md` run.
Branch `phase/p4` off `main` at `014d154` (P3).

## Built

- **`senderFor(ctx)`** (`src/lib/email/sender.ts`): verified own domain →
  `"Nombre" <local@dominio>`; else `EMAIL_DEFAULT_DOMAIN` → the platform's
  default subdomain; else unset, current behaviour. Reply-To is
  `settings.contactEmail`, falling back to the tenant's first active admin.
- **`sendEmail` gains** `from`, `replyTo`, `attachments`, `ctx`, `kind`
  (transactional | automated). With a `ctx` and no explicit `from`/`replyTo`
  it resolves `senderFor(ctx)` itself — so `automations/actions.ts`'s
  `send_email` action picks up its tenant's identity by passing `ctx` and
  `kind: "automated"` through, nothing else. Every send with a `ctx` writes
  an `email_log` row (migration 0032).
- **Own-domain flow**: `tenant_email_domains` (migration 0032),
  `modules/tenancy/email-domains.ts` wraps Resend's Domains API (create →
  DNS records shown with the raw record objects → admin retry or the
  `email.verify_domain` job polls `verify`+`get` every 10 min for 72h, then
  `failed`). No `RESEND_API_KEY` = the row still gets created but stays
  `pending` with nothing to show, same degrade-gracefully rule as Resend
  elsewhere.
- **`maxEmailsPerDay`** plan limit, rolling 24h window over `email_log`
  (`modules/tenancy/limits.ts`).
- **"Enviar por email"** on the quote and nota de venta detail pages
  (`lib/email/document-delivery.ts`'s `sendLinkEmail`): public link + PDF,
  only rendered when the contact has an email.
- **Unsubscribe** `/u/[token]`: stateless, HMAC-signed (tenant id + contact
  id in the token, no table), sets the same `optout` tag the WhatsApp
  BAJA/STOP keyword sets.
- Settings page email section: contact email, add/retry/remove domain, DNS
  records table, per-domain sender local part.

## Decisions and deviations

1. **Touches `modules/automations/actions.ts`** (6 lines: `ctx` and
   `kind: "automated"` added to the existing `sendEmail` call), despite the
   "no changes to automations" hard limit — the exit criterion itself
   ("the send_email action must... pick up senderFor") requires it, and P1's
   own comment anticipated this exact touch. The resolution logic lives
   entirely in lib/email; this call site only opts in.
2. **`sendLinkEmail` writes no quote/document status or activity type** —
   `quote_sent` etc. belong to modules/quotes and modules/documents (P6's
   Owns column). It writes a generic `system` activity
   (`{kind: "quote_emailed" | "document_emailed"}`) instead.
3. **No admin "booking detail" page exists** to hang an email button on —
   `/booking/[id]` is the booking *type* editor, not a reservation record.
   Skipped rather than building the missing page; noted for whichever phase
   adds one.
4. **`contactEmail` added to `TenantSettings`** (no migration, same pattern
   as `reviewLink`) rather than a new tenant column.
5. **Unsubscribe token reuses `APP_ENCRYPTION_KEY`** as the HMAC key rather
   than a new secret — a different operation (signing, not the AES-256-GCM
   use §3.4 reserves it for) on an already-provisioned 32-byte value.
6. **`maxEmailsPerDay` is a rolling 24h window**, not the tenant's calendar
   day — simpler, and a pacing cap doesn't need "the tenant's today" the way
   a promo's "hasta el 30" does.
7. **DNS records are stored and rendered as Resend's raw record objects**,
   not typed field-by-field — the SDK's own `DomainRecords` union already
   carries the shape; the settings table reads `type`/`name`/`value`
   generically.
8. **`domains.verify` then `domains.get`**: `verify` only returns `{id}`,
   no status or records, so a poll both triggers the check and immediately
   reads the result back.

## Known issues

- The unsubscribe route mutates on GET (single click, no confirm) — the
  standard pattern, but a mail client's link-prefetcher can trigger a false
  unsubscribe. Not addressed in this pass.
- The opt-out confirm's server-action round trip (P3's carryover) and this
  phase's own action files are covered at the function level; the
  `sendQuoteByEmailAction`/`sendDocumentByEmailAction` server actions
  themselves have no integration test (no session harness in this repo).
