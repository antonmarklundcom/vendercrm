# O2 — The Claude Ops page (PLAN.md §18.4, §18.5)

Sonnet, Claude Ops wave, phase 2 of two. Branch off `main` at `82fc42e` (O1,
#124).

## Built

- **Page** (`src/app/(superadmin)/claude-ops/page.tsx`): token panel, batch
  bar (roll-up counts + new-batch form), worksheet (Sites / Paste list tabs),
  needs-you list, provisioning log — all server-rendered off O1's tables plus
  `queries.ts`'s tenant/site/pipeline/key joins, batch picked via `?batch=`.
- **Empty state**: no token yet → only the create-token form renders, per
  §18.4.
- **Token panel** (`TokenPanel.tsx`): create with a one-time reveal dialog
  (the `ResetPasswordButton` "show once" idiom, not a fetch-back), prefix +
  last-used + call count afterwards, revoke, and a comma-separated allowlist
  editor.
- **Worksheet** (`Worksheet.tsx`): five-cell step strip (`StepStrip.tsx`), row
  drawer with what was provisioned, credentials, raw pasted detail, and the
  go-live gate (Approve and go live / Reject with note) — shown only while
  `awaiting_approval`.
- **Go-live gate** (`actions.ts`): `approveRowAction` activates the site,
  deletes the test deal then contact (`modules/crm/deletion`, tenancy-walled
  via `buildSystemTenantContext`), marks the row `live`; `rejectRowAction`
  stores the note and sets `needs_input`.
- **Log** (`components/ops/OpsLog.tsx`): `listAuditLog` filtered on any
  `payload.via`, chips this-batch / failures-only / all, link to `/audit`.
- **Nav item** after WhatsApp, `superadmin.ops` i18n block in all three
  message files (es primary).
- **Tests**: `authorization.test.ts` — every action refused for a tenant
  admin, run for a superadmin; approve activates the site and deletes both
  test records; reject stores the note.

## Decisions and deviations

1. **Two functions added to `modules/ops`**: `getOpsTokenRow` (full row,
   `tokens.ts`) so the console can reuse `createOpsBatch` under a real token,
   and `setBatchRawText` (`batches.ts`) for the paste box — neither touches
   the guard; both are superadmin-only console reads/writes, not new token
   power. Logged per the phase rules' "log it".
2. **`createBatchAction` picks the owner's newest non-revoked token itself**
   rather than asking — §18.1.1 expects one token per PC in practice, and the
   page has no other sane place to source one from for a console-created
   batch.
3. **`StepStrip` imports only types from `modules/ops/batches`**, restating
   the five step ids as a local constant, because the barrel (`@/modules/ops`)
   re-exports `provision.ts`, which pulls in `next/headers` through the
   tenancy context — fatal in a client bundle (Worksheet is `"use client"`).
   Found by `npm run build`, not by lint or typecheck.
4. **The failed-row "Resolve" gate from the mockup was dropped**: a failed
   row has no site yet, so there is nothing for the owner to approve — only
   the session can re-run the step. The drawer shows the stored reason and
   nothing else.
5. **Console-side audit writes carry `payload.via = "console:<userId>"`**,
   the same shape token calls carry `ops_token:<prefix>`, so `queries.ts`'s
   log read is one filter over one table.

## Known issues

- The allowlist editor takes a comma-separated tenant-id string, not a
  picker — O1 exposes no tenant-name lookup for arbitrary ids, and adding one
  was out of scope.
- No live screenshot pass: this sandbox has no browser session to drive
  `next dev` interactively. `npm run build` renders `/claude-ops` to a real
  page against the dev DB (empty-state path); the CI artifact step was not
  run.
