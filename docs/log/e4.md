# E4 — Email Inbox and reply (PLAN-EMAIL.md §4)

Opus. Stacked on E2+E3 (branch `phase/email-e4`). No migration in this phase.

## Built

- **`/email`** — thread list (open / closed / all, per-mailbox filter when a
  business has several addresses), unread dot, contact badge. Its own nav
  entry "Correo" next to Bandeja and Chat web, shown only when
  `isMailboxAvailable(ctx)` (platform configured + business switched on);
  the pages and every action 404 / refuse otherwise.
- **`/email/[id]`** — thread view: messages in order, outbound ones tinted
  with a status badge when not sent; HTML as sanitized at ingest; remote
  images blocked with a "Mostrar imágenes" link (`?images=1`); inline `cid:`
  images and attachments through 15-minute signed storage URLs; mark unread,
  close / reopen; contact panel.
- **Contact link** — if the sender isn't a contact yet, a name + phone form
  creates one (source `email`, email filled in) or links the existing
  contact with that phone. Once linked, the thread can be tied to one of
  that contact's deals.
- **Reply** (`modules/mailbox/reply.ts`) — always via `mailboxProvider()`
  (Cloudflare), From = the mailbox address with its display name, To = the
  customer's Reply-To or From, optional Cc; **max 5 recipients** in total;
  plain-text body sent as text + escaped HTML; stored as an outbound
  message (`queued` → `sent` / `failed`). Refused when the business's
  outbound is suspended (`tenants.outbound_suspended_at`) or the mailbox
  address is deactivated. A `guard` hook is where E5 plugs its caps in.
- **Push** for a new inbound email, same channel and 2-minute per-thread
  throttle as an inbound WhatsApp message.
- Provider message gained optional `text`, `cc`, `headers` (Resend path
  unchanged when they're absent).

## Decisions

1. **Own route `/email`, not a tab in `/inbox`** — same reasoning the chat
   widget used (layout.tsx comment): separate channel rules; a unified inbox
   should be a decision.
2. **Threading of the customer's answer to our reply.** Cloudflare sets the
   outgoing Message-ID itself and REST doesn't return it (verified in
   cloudflare-docs `email-service/reference/headers.mdx`). We send
   `In-Reply-To`/`References` pointing at the customer's own message, so
   their answer's References contain an id we have; the subject fallback
   covers the rest. We also send `X-VenderCRM-Message-Id` for E5.
3. **Plain-text composer**, no rich text and no quoting of the previous
   message — keeps it simple and 1-to-1.
4. **HTML rendered inline** (not an iframe): it is sanitized at ingest with
   an allowlist that permits no positioning and no negative margins, and a
   sandboxed iframe can't size itself without scripts.
5. React 19 resets a form after an action; the reply and contact forms get
   their values back in the action state so a failed send doesn't lose the
   typed text (found while testing in the browser).

## Checked by hand

Ran the app locally with the mailbox env set, seeded a business with two
threads, and used it in Chromium (desktop and 390 px mobile): list, thread,
script/onclick stripped, tracker image blocked until "Mostrar imágenes",
contact creation, 6-recipient refusal, failed send recorded and shown with
the typed text kept (the send failed because the Cloudflare token was a dummy).
