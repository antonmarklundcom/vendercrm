# E1 — Mailbox switch + email provider abstraction (PLAN-EMAIL.md §4 E1)

Opus, first of phases E1–E5 (`prompts/opus-e1-cloudflare-mailbox.md`).

## Built

- **Env vars** (`src/lib/config/env.ts`, all optional): `EMAIL_PROVIDER`
  (`resend` default | `cloudflare`), `CLOUDFLARE_ACCOUNT_ID`,
  `CLOUDFLARE_EMAIL_API_TOKEN`, `EMAIL_INBOUND_SECRET`. Documented in
  `.env.example`. None of them can fail boot.
- **Providers** (`src/lib/email/providers/`): one `EmailProvider` interface,
  `resend.ts` (the exact call `sendEmail()` made before) and `cloudflare.ts`
  (REST). `platformProvider()` follows `EMAIL_PROVIDER` and falls back to
  Resend with a warning when Cloudflare is selected but not configured;
  `mailboxProvider()` is Cloudflare-only for E4 replies. `sendEmail()` now
  asks the provider instead of holding a Resend client; its caps, logging,
  sender resolution and never-throw contract are unchanged.
- **Migration `0043_add_tenant_mailbox`**: `tenants.mailbox_enabled`
  (boolean, default false) and `tenants.outbound_suspended_at` (datetime, null).
- **`src/modules/tenancy/mailbox.ts`**: `isMailboxConfigured()`,
  `isMailboxAvailable(ctx)` (env first, so an unconfigured platform never
  reads the DB), `setMailboxEnabled()` and `clearOutboundSuspension()`, both
  audited (`mailbox.enabled` / `mailbox.disabled` / `mailbox.suspension_cleared`).
- **Superadmin tenant page**: "Casilla de correo" section with the on/off
  toggle, a note when the platform vars are missing, and "Quitar suspensión"
  when `outbound_suspended_at` is set. es/en/sv strings.
- **Tests**: `lib/email/defaults-off.test.ts` (no new env → Resend with the
  same payload, no mailbox, no DB read), `lib/email/providers/providers.test.ts`
  (selection, fallback, Cloudflare payload/endpoint/errors/bounce),
  `modules/tenancy/mailbox.integration.test.ts` (toggle, per-tenant scope,
  audit rows, suspension clear).

## Decisions

1. **"Mailbox configured" = Cloudflare account id + token + inbound secret.**
   The plan ties Inbox visibility to `EMAIL_INBOUND_SECRET`; replies (E4)
   also need the Cloudflare pair, so an Inbox without them would be
   read-only and confusing. All three are required.
2. **`isMailboxAvailable` is not wired into nav yet.** There is no Inbox UI
   until E4, so there is nothing to show or hide; E4 adds the nav entry
   behind this helper.
3. **A permanent bounce in the Cloudflare response counts as a failed send**
   (`email_log.status = failed`), so E5's bounce rate can read it later.
4. **Cloudflare REST gives no message id**, so `email_log.provider_id` stays
   null for Cloudflare sends. E5 may need another way to correlate bounces.

## Cloudflare API details — verified vs not

Verified against the Cloudflare docs source (github.com/cloudflare/cloudflare-docs,
`email-service/api/send-emails/rest-api.mdx`, `examples/email-sending/recipients.mdx`;
developers.cloudflare.com itself was blocked from the build container):
endpoint `POST /client/v4/accounts/{id}/email/sending/send`, Bearer token,
fields `to`, `from` (string or `{ address, name }`), `subject`, `html`,
`reply_to`, `attachments[{content (base64), filename, type, disposition}]`,
response `{ success, errors[{code,message}], result{delivered, permanent_bounces, queued} }`.

Not verified: whether `attachments[].type` is required (we always send it,
guessed from the file extension); whether `reply_to` accepts `{address,name}`
(we send it in the same shape as `from`); exact API-token permission name.
**Not exercised against the live API** — no Cloudflare account in CI.

## Anton sets up by hand (nothing needed for this phase to deploy)

This phase ships dark: deploy as is, nothing changes. When going live
(PLAN-EMAIL.md §5):
1. Cloudflare account → Workers Paid ($5/month).
2. Move one test domain's nameservers to Cloudflare; enable Email Routing and
   Email Sending on it.
3. Create an API token with Email Sending permission only.
4. On Hostinger set `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_API_TOKEN`,
   `EMAIL_INBOUND_SECRET` (random, 32+ chars; the E2 Worker gets the same
   value) and redeploy. Leave `EMAIL_PROVIDER` unset (= resend).
5. Run the migration (`npm run db:migrate`) — `0043` adds two columns to `tenants`.
6. Superadmin → the test business → "Activar casilla". (Nothing visible to
   the tenant until E4 ships.)
7. Only after the mailbox is proven: `EMAIL_PROVIDER=cloudflare`.
