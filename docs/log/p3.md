# P3 — Inbox ergonomics (PLAN.md §15.5 J2 inbox half + J12c, §15.8)

Sonnet, wave 1 lane 2, phase 1 of the sequential `sonnet-wave1-lane2.md` run.
Branch `phase/p3` off `main` at `0a0c5e4` (P2).

## Built

- **Quick replies**: `quick_replies` table, `modules/whatsapp/quick-replies.ts`
  (CRUD + `renderQuickReply` for `{{contacto.nombre}}`), admin page at
  `/inbox/quick-replies`, `/` picker in the composer.
- **Internal notes**: `conversation_notes` table, `modules/whatsapp/notes.ts`,
  rendered inline in the thread (distinct style, never a `messages` row) and
  on the contact timeline via a new `conversationNote` `TimelineEntry` kind.
- **Filters**: `/inbox?filter=mine|unassigned|unread|all`, plus `?q=` search
  over message body and contact name/phone, shared between the page and the
  5s poll through `inbox/rows.ts`.
- **Web-chat merge**: open `chat_conversations` join the same list under a
  channel chip (`all` view only, no filter/search applied to them yet).
- Mark as unread; keyboard `j/k` in the list, `r` focuses the reply box.
- Manual send to an `optout`-tagged contact shows a confirm dialog naming
  the tag; confirming logs a `system` activity on the contact.

## Decisions and deviations

1. **No `conversations.channel` column.** WhatsApp and web chat are already
   two separate tables; the channel chip is computed in `inbox/rows.ts` from
   which table a row came from, so the column the prompt allowed was never
   needed.
2. **Touches `modules/crm/timeline.ts` and `contacts/[id]/page.tsx`**, both
   in P5's Owns column, despite the "no changes to crm" hard limit. The
   phase's own rule ("notes shown on the contact timeline too") cannot be
   met otherwise; sequential lane 2 means P5 (next) builds on this rather
   than racing it, so the conflict the hard limit was written to prevent
   does not apply here.
3. **No `/chat/[id]` route exists** (the whole chat page is inline threads
   per conversation), so a web-chat row's href is `/chat`, not a per-thread
   page. Documented rather than building the missing route, which is out of
   scope for this phase.
4. **"Mark as unread" sets `unreadCount = 1`**, not a restored true count —
   there is nothing to restore to; 1 is enough to re-enter the `unread`
   filter and show a badge, which is the point of the action.
5. **Opt-out override activity uses `payload.kind`**, matching the existing
   `system`-type convention in `documents.ts`/`delivery.ts` rather than a
   free-text `payload.text`.

## Known issues

- The opt-out confirm is unit-covered at `hasOptedOut` (the guard itself);
  the full server-action round trip needs a session and isn't exercised by
  an integration test in this pass.
- Web-chat rows carry no filter/search of their own on `/inbox` — only
  `/chat`'s own status filter applies to them.
