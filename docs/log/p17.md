# P17 — Forms field editor (PLAN.md §15.5 J11b, §17.2, §17.3 "P15/P17" P17 half)

Sonnet, wave 2 lane 2, phase 5 of the sequential `sonnet-wave2-lane2.md` run.
Branch `phase/p17` off `main` (after P16 + its index line).

## Built

- **`modules/forms/field-definitions.ts`** (new): owns the field-list shape
  and every rule around it, shared by the editor action and the public
  submission path.
  - `FORM_FIELD_TYPES`: `text/phone/email/select/textarea` (§4) plus
    `checkbox` and `date`.
  - `validateFormFields(fields, customFieldKeys)`: parses with zod, then
    enforces exactly one *required* `phone` field, unique keys, a `select`
    field having at least one option, and every `mapTo` naming a custom
    field the tenant actually has.
  - `slugifyFieldKey`: same slug convention P5's custom-field keys use
    (`custom-fields.ts`), so a form field key and a `mapTo` key never drift
    into subtly different shapes.
  - `assertKeysNotRenamed`: refuses to change a surviving field's key once
    the form has a submission — matched by an explicit `originalKey` the
    editor tags each row with (not array position, since reordering is a
    supported operation and must not read as a rename).
  - `validateSubmissionData`: re-checks required/select constraints
    server-side on every public submission.
- **`/forms/[id]`**: the field editor. Add/remove/reorder (up/down buttons,
  no DnD library) and edit label/type/required/options/`mapTo` for every
  field; a form with submissions shows a locked notice and disables the type
  selector on surviving fields (their `key` can't move). One `useActionState`
  action (`updateFormFieldsAction`) validates and saves the whole list.
  Existing forms (`STANDARD_FIELDS`, unchanged since before this phase) open
  in the editor exactly as they were.
- **Public form page**: renders `checkbox` and `date` alongside the existing
  types. `submitForm` re-validates against the definitions server-side, then
  writes every `mapTo`-mapped answer into `contacts.custom` through
  `updateContact` — the same merge-not-replace path the contact edit form
  uses — using `coerceCustomFieldValue` (P5) so a stray unparseable value is
  dropped rather than corrupting the field.
- **`contacts.wa_marketing_consent_at`**: does not exist on `main` (P10, lane
  1, not merged when this phase ran). Per the phase's documented fallback,
  the `checkbox` field type still ships and a tenant can add a
  `consent_whatsapp` field today; the actual consent stamp is a one-line
  `KNOWN-ISSUES.md` entry, to be wired once P10 merges.

## Decisions and deviations

1. **The editor posts one JSON blob, not per-row indexed inputs.** Add/
   remove/reorder need client state regardless (no DnD library, but still
   dynamic rows), so the component is already `"use client"` — a hidden
   input carrying the serialized field list is simpler than reinventing
   indexed `fields[3].label`-style form fields for no progressive-enhancement
   benefit a client component doesn't already forfeit.
2. **Key-rename detection is by explicit tag, not array position.** A naive
   "compare old[i].key to new[i].key" would treat a legitimate reorder as a
   rename. Each editor row instead carries the key it started as
   (`originalKey`, `null` for a brand-new row); only a surviving row whose
   key changed is refused.
3. **`mapTo` values are written after `recordLeadSubmission`, not inside
   it.** The ingest engine is explicitly out of scope for this phase (its
   own hard limit); `submitForm` calls `updateContact` itself once it has
   the resulting `contactId`, the same two-step shape the CSV importer
   already uses (create/find the contact, then merge in custom values).

## Known issues

- Consent stamping is not wired — see above and the matching
  `KNOWN-ISSUES.md` entry; the checkbox field type and its data are otherwise
  fully functional (a ticked box just answers `"1"` in the submission
  payload today).
- The public-facing errors this phase adds (`field_required:<key>`,
  `invalid_option:<key>`) are stable codes thrown the same way
  `phone_required`/`turnstile_failed` already were — none of these are
  currently caught into a friendly visitor-facing message; that gap predates
  this phase and is out of its scope.
