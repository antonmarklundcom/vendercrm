# P7 — "Hoy" panel, rule-based coach (PLAN.md §15.3 L1, §15.5 J6, §15.8)

Sonnet, wave 1 lane 2, phase 5 of the sequential `sonnet-wave1-lane2.md` run.
Branch `phase/p7` off `main` at `cd0ed4e` (P6 + its index line).

## Built

- **`modules/coach/rank.ts`** (pure, DB-free): six rule kinds — unread
  conversation (unread, last inbound 60+ min ago, inside business hours),
  overdue task, upcoming booking (confirmed, next 24h, no
  `reminder_sent_at`), unreplied quote (`sent` 3+ days, no activity on the
  contact since, no open task), stale deal (`stage_entered_at` past
  `stages.stale_after_days`, falling back to 7 when null), lead without a
  deal (`lead_submissions` in the last 48h with no `deal_id`). Fixed
  severity + priority per kind; within a kind, most urgent first. A `mine`
  option filters to one user's own assignments — an item nobody owns yet
  (an unassigned conversation, a lead) never appears under `mine`.
  `isWithinBusinessHours` reads `tenants.settings.businessHours` in the
  tenant's own timezone via `modules/calendar/zoned-time.ts`.
- **`modules/coach/hoy.ts`**: `buildHoy(ctx, now, {mine?})` — the DB reads
  (each module's own exported list function where one existed; a direct
  `tenantDb(ctx).select(table)` for deals/stages/contacts/activities, the
  same pattern `modules/dashboard/summary.ts` already uses for tables it
  doesn't own), the cross-referencing between them, then one tenant-locale
  render into `{kind, severity, title, subtitle, url, action}` via
  `getTranslator`.
- **Dashboard**: the Hoy panel renders at the top of `/dashboard`, above the
  stat cards — one row per item, a severity dot, and the deep-link action
  button. Empty state when nothing needs attention.
- **Morning push**: `coach.morning` (self-rescheduling hourly) checks every
  tenant's local wall clock; a tenant whose clock currently reads 08:xx gets
  one `buildHoy(ctx, now, {mine: user.id})` per (non-banned) member, and — if
  their list isn't empty — one `notifications` row (`kind: "system"`,
  the count and top-three titles), which is what carries P2's web push.

## Decisions and deviations

1. **"Tenant timezone 08:00" without a new column.** A per-tenant precise
   schedule needs somewhere to remember "already sent today", and this phase
   has no schema of its own. The chain runs hourly instead of daily and only
   acts on a tenant currently inside its local 08:00 hour — one pass per
   tenant per day, no state to persist, and no PLAN.md schema change.
2. **`buildHoy` renders in the tenant's locale, not the viewer's.** §15.3
   says the same list is the body of both the dashboard panel and the
   morning push — one render shared by both call sites is what makes that
   true, and a coach speaking the business's own language regardless of
   which teammate is logged in matches the reasoning P4's transactional
   emails already use.
3. **A quote's "no activity since" reads the contact's activity trail, not
   the quote's own** — `activities` has no `quote_id` to key on. A rep who
   called or noted anything about this customer after sending the quote has
   already followed up, whatever the note says.
4. **No exported function added to `crm/deals.ts` or `crm/contacts.ts`.**
   `dashboard/summary.ts` already reads `deals`, `stages`, `contacts` and
   `activities` directly through `tenantDb(ctx).select(table)` for exactly
   the same reason (no all-rows list function exists for them); this phase
   follows that precedent instead of adding a new one-off function to a
   module it doesn't own.
5. **A booking/lead/quote's `mine` ownership is inherited from its deal**
   (`deals.assigned_user_id`) **when it has one, else null.** Neither table
   carries its own assignee; a lead with no deal yet is nobody's to claim.
6. **`worker/index.ts` and `worker/maintenance.ts` touched again** (P1/P2/
   P4/P6 precedent) to import and seed the new hourly chain.

## Known issues

- `sendMorningDigests` re-runs `buildHoy` once per user in a tenant rather
  than once per tenant — correct (each user's list differs), but means the
  tenant-wide reads (conversations, deals, quotes…) repeat per user. Fine at
  current scale; worth a per-tenant cache inside one run if the member count
  grows.
- The hourly check's own execution time can drift its next `runAt` by
  seconds; negligible against a 60-minute window, but a very slow run could
  in principle land the digest for one tenant on the wrong side of its 08:00
  boundary on a given day.
- `upcoming_booking`'s `mine` ownership and the dashboard panel do not
  distinguish a booking with no linked deal from one whose deal has no
  assignee — both show as unowned, same as a lead without a deal.
