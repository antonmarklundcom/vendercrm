# P2 — Web push on the PWA (PLAN.md §15.5 J2 push half, §15.8)

Opus, wave 1 lane 1, last lane 1 phase. Branch `phase/p2` off `main` at
`f2e96b6` (P1).

## Built

- **Keys**: `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`,
  `WEB_PUSH_SUBJECT`, all optional, documented in `.env.example`, generated
  by `npm run generate-vapid` (`scripts/generate-vapid.ts`, prints rather
  than writes). Absent keys hide the feature the way Resend and Sentry are
  hidden: no control renders, `/api/push/subscribe` answers 404, and
  `enqueuePush` returns without writing a job — so an unconfigured platform
  does not accumulate a queue row per notification.
- **Rows**: `push_subscriptions` (tenant, user, endpoint unique, p256dh,
  auth, user_agent, created_at, last_seen_at, failed_at) and
  `users.push_prefs` json, migration 0030.
- **Route**: `POST`/`DELETE /api/push/subscribe`, session-guarded through
  `lib/api/guards` — the tenant and user come from the session, never the
  body.
- **Worker**: job kind `push.send` (tenant, user, kind, payload), one job per
  recipient, `maxAttempts: 2`. 404/410 from the push service deletes the
  subscription; any other failure stamps `failed_at` and keeps it.
- **Enqueued on**: every `notifications` row (the hook is inside
  `createNotification`, so `notify_user` and anything a later phase writes
  are carried without touching that phase); an inbound WhatsApp message; a
  conversation being assigned; the daily task/appointment reminder.
- **Service worker**: `public/sw.js` — push → `showNotification` with the
  url, click → focus-or-open. No fetch handler and no caching in this pass.
- **UI**: `PushRegistrar` in the signed-in layout registers the worker and
  shows the one-time inbox banner on mobile; `PushToggle` +
  `PushPrefsForm` in settings, for both admins and agents.
- **Muting**: four kinds in settings (`inbound_message`, `assignment`,
  `task_due`, `automation`). `system` is deliberately not mutable.

## Decisions and deviations

1. **An inbound message is the one push with no `notifications` row.**
   Everything else reaches a phone by way of a row. Inbound messages already
   have a home — the inbox and its unread count — and mirroring every one
   into the bell would bury the notifications that actually ask somebody to
   do something. The push is the nudge, the inbox is the record.
2. **`push_prefs` stores only what was switched off.** NULL, `{}`, an
   unparseable value and a row written before a kind existed all mean
   "everything on", so a kind added later is on for everyone with no
   backfill, and no failure mode ends in silence.
3. **The two-minute per-conversation cap is in memory**
   (`fanout.ts:ConversationPushThrottle`). §2.1 pins this to a single Node
   process where the webhook and the worker are the same process. A restart
   lets one extra push through per conversation, which is not worth a table,
   a row lock and a write on the hottest path in the product. If the worker
   is ever lifted out (§2.1, §15.6) this becomes a column on
   `conversations` and no caller changes.
4. **`endpoint` is unique platform-wide, not per tenant.** A browser is one
   browser: re-subscribing after switching business, or after somebody else
   signs in on the same phone, has to *move* the row, or the previous owner
   goes on receiving another business's customers. That requires one
   delete-by-endpoint outside any tenant scope, so
   `src/modules/notifications/**` joins the raw-db exemptions in
   `eslint.config.mjs`, with the same shape of justification as the webhook
   and public-token lookups already there. Everything else in the module
   goes through `tenantDb`.
5. **Assignment is announced, not notified.** `assignConversation` emits a
   new `wa.conversation_assigned` on the WhatsApp bus and the notifications
   module decides who wants telling — rather than the inbox importing
   notifications. Assigning to yourself, and unassigning, notify nobody.
6. **`sendPush` uses `getActiveTenantUser`, not `getUserById`.** A
   salesperson who left last week still owns deals, so an automation can
   still resolve `notify_user` onto them; the platform-level `banned` flag
   would not have stopped that push. This is the same check every request
   goes through.
7. **`/sw.js` is in `middleware.ts`'s `PUBLIC_EXACT`.** The repo's own
   allowlist test caught it. Registration always carries a session, but the
   browser re-fetches the worker script on its own schedule, and a 307 to
   `/login` on a lapsed session makes a browser tear the registration down —
   push would then stop permanently for anyone who left the app closed over
   a weekend.
8. **The inbox banner is rendered from the layout**, gated on `usePathname()`
   and `md:hidden`, rather than from `inbox/page.tsx` — that file is P3's,
   and this keeps the whole feature at one mount point.
9. **`src/app/manifest.ts` is unchanged.** It is in P2's Owns column, but
   nothing web push needs is missing from it: name, icons, `start_url` and
   `display: standalone` are all already there, and VAPID needs no
   `gcm_sender_id`.
10. **Files touched outside the Owns column**, all of them small and none
    with a concurrent writer (lane 1 is sequential and every lane 2 phase
    starts after this merges): `middleware.ts` (#7), `eslint.config.mjs`
    (#4), `whatsapp/events.ts` + `whatsapp/inbox.ts` (#5),
    `crm/task-reminders.ts` (the task-due notification),
    `tenancy/users.ts` + `tenancy.ts` schema (`push_prefs` and its setter),
    `worker/index.ts` (one import), `(app)/layout.tsx` (the registrar),
    `(app)/settings/page.tsx` + `actions.ts` (the controls).

## Known issues

- A user removed from a business keeps their `push_subscriptions` rows.
  Nothing is delivered to them (#6 refuses before the send), so this is dead
  weight rather than a leak; a sweep belongs with whatever phase first needs
  to enumerate a departing user's data.
- The inbound throttle claims its window before checking whether anybody is
  subscribed, so a burst into a tenant with no subscriptions still consumes
  it. Costs nothing — there was no push either way.
- P1 noted `countUnread` counts rows in Node rather than with `count(*)` and
  suggested folding it into P2. Left alone: the bell still reads ten rows on
  a page the layout already renders, and nothing in this phase changed its
  scale.
- iPhones get the `notifications` row and no push unless the PWA is
  installed from Safari. Expected — Apple's rule, and the reason the row is
  the source of truth.

## Where P3 should look first

`src/modules/notifications/hooks.ts` is where an inbound message becomes a
push, and it reads `conversations.assignedUserId` — the inbox work will
change what "assigned" means in a few places, and `recipientsForInbound` in
`fanout.ts` is the one function to keep in step. The new
`wa.conversation_assigned` event on `whatsapp/events.ts` is emitted from
`assignConversation`; anything P3 adds that reassigns a conversation should
emit it too, or the new owner is not told.

`/inbox/<conversationId>` is the URL every inbound push lands on. If P3
changes that route shape, `hooks.ts` and the assignment notification both
need the new one.
