# K3 — Memory imports, template variables, coach rows (PLAN.md §16.6)

Sonnet, run directly in a Claude Code session (same as K2 — the owner asked
for it explicitly rather than a separate Opus/Sonnet lane session), on top
of `main` after K2 (#121) merged. K3's own prompt hard-depends on K2 and was
skipped in the earlier wave for exactly that reason (`KNOWN-ISSUES.md`).

## Built

- **Imports** (`modules/memory/imports.ts`, `/settings/negocio/importar`):
  paste text, upload a PDF, or give a URL. One `generateStructured` call
  (schema: up to 20 `{kind, title, body}` candidates) turns the source into
  facts written `source: ai_suggested`, unconfirmed (§16.2 rule 2) — no new
  review screen was needed, since K1 already built confirm/edit/delete for
  exactly this state on `/settings/negocio`. `memory_imports` (K1's table,
  unused until now) tracks status/extractedCount/aiReplyId/error per import.
  - PDF: `pdfjs-dist` (new dependency — none existed) reads the text layer
    page by page, no rendering/canvas involved. Started as `pdf-parse`, but
    its bundled pdf.js is years stale and rejects perfectly ordinary modern
    PDFs (including react-pdf's own output, caught by this phase's own PDF
    test in CI) with "bad XRef entry" — switched to pdfjs-dist directly,
    Mozilla's actively maintained engine that every such wrapper sits on
    top of anyway. A scan with no text layer is reported as
    `pdf_no_text_layer`, never OCR'd.
  - URL: same-tenant rate limit (10/hour), a 200 KB response cap, and a
    regex-based `html-to-text.ts` (script/style stripped, then every tag) —
    no DOM-parser dependency for what is, at this scope, a services/FAQ page.
  - Ledger `kind: "memory_extract"` already existed on `ai_replies` (K1);
    the tenant's daily cap and "no driver configured" both end the import
    `failed` with a reason, never throw.
- **Template variables** — `{{negocio.nombre|horario|direccion|
  politica.cancelacion|politica.senas|pagos}}` (`modules/memory/vars.ts`):
  `getNegocioVars(ctx)` reads the profile + confirmed, customer-visible
  `location`/`policy` facts (`resolveHours`, exported from `retrieve.ts` for
  this). Registered in `contracts/render.ts`'s `isKnownVariable`/
  `renderContractBody` — the concrete, tracked gap (`KNOWN-ISSUES.md`: "a
  contract template referencing `negocio.*` is refused at save"). Also wired
  into the quote and nota de venta PDFs' footers (`paymentMethods`,
  `depositPolicy`, printed only when confirmed and present).
- **Coach rows** (`modules/coach/hoy.ts`, `rank.ts`): three new low-severity
  `HoyItemKind`s — `memory_incomplete` (profile below 60% complete),
  `fact_review_due` (a confirmed fact past `review_after`), `promo_expired`
  (a confirmed promo whose `validUntil` has passed) — all linking to
  `/settings/negocio`, the one page that fixes any of them.
- **Public booking page**: address + maps link, read via `getProfile`
  against the same system tenant context `getPublicBookingType` already
  resolves (`resolved.ctx`) — no new public-data-access path needed.

## Decisions and deviations

1. **Built by a Sonnet session, no separate lane.** Same call as K2: the
   owner asked directly, and nothing here needs Opus specifically.
2. **No separate review screen for imports.** The prompt's own file list
   implies one might be needed; K1's `/settings/negocio` already shows
   every unconfirmed fact with confirm/edit/delete per row, badged
   `aiSuggested`. Building a second one would duplicate that UI for no
   reason — the import page's whole job is getting a source *in*.
3. **`negocio.*` variables were NOT added to the automations/flow message
   registry** (`renderTemplateVars` in `automations/actions.ts`), only to
   contracts. The prompt's "documented in the FlowEditor variable help"
   line has no concrete tracked gap behind it (unlike contracts, which
   `KNOWN-ISSUES.md` explicitly names), and wiring it into every flow
   action handler would mean threading `ctx` through call sites this phase
   has no verified need to touch. `modules/memory/vars.ts`'s
   `renderNegocioVars` is exported and ready for whichever phase does want
   it there.
4. **`policies`' single conversation question maps to one `policy` fact
   with `structured.topic` per confirmed fact** — `getNegocioVars` looks
   up `negocio.politica.cancelacion` and `negocio.politica.senas` by
   `structured.topic` (`cancellation`/`deposit`), so it resolves correctly
   however many separate policy facts an admin (or an import) ends up
   creating; nothing assumes there is exactly one.
5. **`negocio.pagos` falls back to a `payment`-topic policy fact** when the
   profile's `paymentMethods` array is empty — some tenants will describe
   payment methods as prose ("transferencia o efectivo") rather than as
   the settings form's list.

## Known issues

- **DB-backed suites** (`imports.integration.test.ts`, the extended
  `hoy.test.ts` case) **cannot run in this build container — no MySQL —
  so they were verified in CI, not locally**, same as every prior phase
  that touched the memory module.
- **The URL importer has no allowlist/denylist** beyond the same-tenant
  rate limit and the 200 KB cap — an admin could point it at an internal
  or unexpected URL. Acceptable for an admin-only action reading a page
  they chose, same trust level as the existing CSV/contact imports.
- **No manual re-extraction retry UI** on `/settings/negocio/importar` —
  a failed import shows its error via the query string once; retrying
  means submitting the form again with the same source.
