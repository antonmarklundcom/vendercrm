# W1 — WhatsApp voice notes, transcribed (PLAN.md §15.3 Lane A, §15.10)

Opus, wave 2 lane 1, phase 1 of `opus-wave2-lane1.md`. Built on the wave 2
plan commit, on the same branch (see Decisions 6).

## Built

- **Driver seam**: `transcribeAudio({audio, mimeType, languageHint})` on
  `AiDriver`, implemented on both drivers — OpenAI via multipart
  `/audio/transcriptions` (its own model, `AI_TRANSCRIBE_MODEL`, default
  `gpt-4o-mini-transcribe`), Gemini via an `inline_data` part on the ordinary
  `generateContent` call. Same result shape as the other two calls, so the
  `ai_replies` ledger and the per-tenant daily cap meter audio with no new
  accounting (`kind: "transcription"`).
- **Schema** (`0035`): `messages.media_mime_type`, `transcript`,
  `transcript_status`, `transcript_model`, `transcript_at`,
  `transcript_error`. Additive, no backfill.
- **`modules/whatsapp/transcription.ts`**: reads the object the webhook
  already stored in R2, guards (not audio, no media, already done, no driver,
  over the tenant's daily AI cap, over 16 MB), writes a terminal
  `transcript_status` in every branch, and records the ledger row. A provider
  error is written *and* rethrown so the queue's backoff retries it.
- **Job `whatsapp.transcribe`**, enqueued by the webhook for an inbound audio
  when a driver is configured; the row is written `pending` at the same time.
- **Deferred chain**: `wa.message_received` now carries `transcriptPending`,
  and a new `wa.message_transcribed` fires when the job reaches a terminal
  state. The automations listener (opt-out, handoff keyword, wait-for-reply,
  `wa_message_received` flows — and through them the AI auto-reply) runs on
  exactly one of the two, so a voice note is answered once, with words in it.
  Notifications and push still fire on arrival, undelayed.
- **Prompt + search**: `messageText()` makes a `done` transcript the model's
  view of an audio message (`toTurns`, `buildReplyPrompt`, the memory query);
  inbox search matches transcripts as well as bodies.
- **Inbox**: an audio bubble with a player (signed, expiring URL minted per
  read by `toThreadMessages`, shared by the page and the 5s poll) and the
  transcript under it — pending shimmer, and a translated one-line reason for
  a `failed`/`skipped` one.
- **Coach voice** (`modules/coach/voice.ts`): a voice note from the number in
  the new `settings.coachPhone`, matching a short intent list, is answered
  with the same `buildHoy` list the dashboard and the morning digest show.
  Settings section + admin action to set the number; empty turns it off.

## Decisions and deviations

1. **Byte cap, not duration.** §15.10 W1 asked for a 10-minute limit too;
   neither the webhook payload nor the stored object carries a duration, and
   decoding the container to find one would cost more than the transcription.
   The 16 MB cap stands in for it (an opus voice note is ~1 MB for ten
   minutes), and `MAX_AUDIO_BYTES` says so.
2. **Transcriptions no longer count against the *per-conversation* reply
   cap** (`countRepliesTodayForConversation` now filters `kind = reply`).
   Three voice notes would otherwise use up a thread's whole daily allowance
   to be answered. They still count against the per-tenant budget, which is
   the one that bounds spend.
3. **Deferral rather than a second reply.** The alternative — reply now,
   re-reply after transcription — double-fires every flow on an audio.
4. **The failed-transcription reason is shown, but only when it is one of our
   own skip codes**; a provider's error string is stored for support and not
   rendered to a rep.
5. **`coachPhone` is a tenant setting, not a user column.** Users have no
   phone, and the owner's personal number is a business fact, not a login.
6. **One branch, not `phase/w1`.** This session's designated branch is
   `claude/opus-wave2-lane1-prompt-vz9f47` and it may not push to another, so
   the wave 2 plan and this phase share it. The lane file's per-phase branch
   loop stands for sessions that can use it.

## Known issues

- **Old voice notes are not backfilled** — only audio received after this
  deploy is transcribed.
- **No manual "transcribe this" button**: a message whose transcription was
  skipped for the daily cap stays skipped until someone re-sends it.
- **`isLastAttempt` finds the job by a JSON payload match**, not by job id —
  the handler signature does not receive one. Correct because a message has
  exactly one transcribe job, but it is a scan.
- **Outbound audio is never transcribed** (nobody asked; the rep wrote it).
- **The coach answer is capped at five items** and is text, not a voice reply.
- **The audio player is the only media rendered in the thread** — images,
  video and documents still show as an empty bubble, as before this phase.
