# E5 — Blast-radius guard (PLAN-EMAIL.md §4)

Opus. Stacked on E4 (branch `phase/email-e5`). No migration (the new
`complained` message status is a Drizzle-level enum on a varchar).

## Built

- **Daily cap per business** (`modules/mailbox/guard.ts`): rolling 24 h,
  `min(200, plan.maxEmailsPerDay)`; **warm-up** 20/day for the first 14 days
  after the business's first mailbox address. Counted: outbound mailbox
  messages queued / sent / bounced / complained (not ones the provider
  refused outright). Refusal shows "Se alcanzó el límite de correos de hoy".
  The superadmin tenant page shows "Enviados en las últimas 24 h: X de Y".
- **1-to-1 only**: max 5 recipients (E4), no Bcc, no bulk/CSV path.
- **Circuit breaker** (`modules/mailbox/breaker.ts`): over the last 50
  sends, more than 3 % bounced (2+) or 2+ spam complaints →
  `tenants.outbound_suspended_at`, audit `mailbox.outbound_suspended`
  (once), email to every superadmin, bell notification to the business's
  admins, banner on `/email`. Only sends after the last "Quitar
  suspensión" count, so clearing it isn't undone by the old bounces.
- **Signals**:
  1. Synchronous: Cloudflare's send response lists the recipient under
     `permanent_bounces` → message `bounced`, breaker evaluated.
  2. Asynchronous: Cloudflare **Email Sending event subscriptions** (Queues;
     `message.bounced`, `message.complained`) → the Worker's new `queue()`
     consumer → signed `POST /api/v1/email/events` → matched to the send by
     mailbox address + recipient (newest within 7 days, same subject
     preferred), since Cloudflare's own messageId isn't one we know.
     Other event types are acknowledged and ignored.

## Decisions

1. **Thresholds read literally**: ">3 % over the last 50 sends" = 2 bounces
   in the 50-send window (the denominator is always 50, so a new business
   with 3 sends isn't tripped by one bounce). The plan's "any complaint
   spike" is set at 2 complaints in the window — one angry customer marking
   one reply as spam shouldn't stop a business.
2. **Default cap 200/day** per business (a constant, `MAILBOX_DAILY_CAP`) —
   far above what 1-to-1 replies need, low enough that one business can't
   eat the 3,000/month included quota on its own in a day.
3. **Bounce DSN emails** sent back to the mailbox address are stored as
   ordinary inbound mail, not parsed: Cloudflare's Return-Path points to its
   own bounce processor, so the event subscription is the reliable signal.

# Go-live checklist (E1–E5), for Anton

### A. Before merging anything — database (PowerShell on your PC)

The app doesn't run migrations on boot. E1 adds columns the app reads on
every page, so **run the migrations before the merged code deploys**.

1. hPanel → Databases → **Remote MySQL** → add your current public IP.
2. In PowerShell, in your local clone, on the E5 branch (it contains all
   migrations 0043 and 0044):
   ```powershell
   git fetch origin
   git checkout phase/email-e5
   npm ci
   $env:DATABASE_URL = "mysql://USER:PASSWORD@EXTERNAL_HOST:3306/DBNAME"
   npx drizzle-kit migrate
   ```
   (external host/port from the Remote MySQL page; see docs/DEPLOY.md §2).
3. Merge the PRs in order: E1 → E2+E3 → E4 → E5. Nothing changes for any
   business until the steps below are done.

### B. Cloudflare (only when you want to switch it on)

1. Workers Paid plan ($5/month, whole account).
2. Add the test domain, compare DNS records with Hostinger (A/AAAA to the
   Hostinger IP), change nameservers at Hostinger, wait for "Active".
   **If the domain uses Hostinger email today, inbound mail moves to
   Cloudflare when Email Routing is enabled.**
3. Email Routing on for the domain; Email Sending on for the domain.
4. API token with only **Email Sending** permission; note the Account ID.
5. R2 bucket. On Hostinger: `STORAGE_DRIVER=s3` and `S3_ENDPOINT`,
   `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` for it (R2 API
   token with read/write on that bucket). If the app already uses R2, reuse it.
6. Queue `vendercrm-email-events`, then Email Sending → the domain → event
   subscription → that queue (bounced + complained at least).
7. Worker: `cd workers/email-inbound; npm install`, edit `wrangler.toml`
   (`bucket_name`, `INBOUND_URL`, `EVENTS_URL` with your CRM URL), then
   `npx wrangler login`, `npx wrangler secret put EMAIL_INBOUND_SECRET`,
   `npx wrangler deploy`.
8. Email Routing → catch-all → **Send to a Worker** → `vendercrm-email-inbound`.

### C. VenderCRM

1. Hostinger env: `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_EMAIL_API_TOKEN`,
   `EMAIL_INBOUND_SECRET` (same value as the Worker), keep
   `EMAIL_PROVIDER` unset. Redeploy/restart.
2. Superadmin → the test business → Casilla de correo → add
   `contacto@domain` (tick "Recibe todo el dominio" if wanted) → **Activar casilla**.
3. Send a mail to the address from your own Gmail → it appears under
   **Correo** in that business → reply → check it arrives, and that your
   answer to the reply lands in the same thread.
4. Only after that: other businesses, and optionally `EMAIL_PROVIDER=cloudflare`.
