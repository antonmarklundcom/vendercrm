# O1 — Ops token, guard and create-only endpoints (PLAN.md §18.1–§18.3, §18.5)

Opus, Claude Ops wave, phase 1 of two. Branch off `main` at `1aff640` (the
§18 planning merge, #123). O2 (`prompts/sonnet-o2-ops-console.md`) builds the
page on these tables.

## Built

- **Schema** (`src/db/schema/ops.ts`, migration 0041): `ops_tokens` (owner,
  label, sha256 hash + prefix, `allowed_tenant_ids`, expiry, revoked,
  last-used, call count), `ops_batches`, `ops_batch_rows` (domain, details,
  five step states, `last_error`, the created ids), `ops_objects` (the
  guard's memory, unique on entity+id). No `tenant_id` on any of them: they
  are platform-level, like `tenants` itself.
- **Token** (`modules/ops/tokens.ts`): `vc_ops_` + 32 random bytes, hashed
  and prefixed exactly like `site_api_keys`, plaintext returned once.
  Create / list / get / revoke / set-allowlist for the O2 page; resolution
  answers null for wrong, revoked and expired alike.
- **Guard** (`modules/ops/guard.ts`): one question — is this object in
  `ops_objects` for this token — plus the single allowlist exception, which
  unlocks site-creation in a named tenant and nothing else. Refusals are 404,
  never 403, so a token never learns that an id it may not touch exists.
- **Batches/rows** (`modules/ops/batches.ts`): own-batch-only reads, row
  writes, step bookkeeping (`markStepDone` / `markStepFailed`), and the
  superadmin-side reads and `markRowLive` / `markRowRejected` O2 needs.
- **The five steps** (`modules/ops/provision.ts`), each idempotent per (row,
  step): tenant + first admin (random password, reset e-mail, nothing
  returned), site (born inactive), pipeline + stages + missing tags + owner
  resolution + the site's routing defaults, API key (plaintext once), test
  lead (`allowInactive`) → row `awaiting_approval`.
- **Routes** (`src/app/api/ops/v1/**`, ten files): `/me`, batches, rows, and
  the five steps, `X-Ops-Token`, zod bodies, `lib/api/guards` error shape,
  120 calls/min/token. `modules/ops/http.ts` holds auth, parsing and
  serialization so route files stay four lines of intent.
- **Two checks the first draft did not have**, both found in this phase's own
  re-read: `row.tenant_id` is writable by the session, so `updateOpsRow`
  refuses to move a row's business once the tenant step has run, and the
  pipeline/key/test-lead steps read the site back *through the row's tenant
  context* (`resolveOpsSite`) — without that, a PATCH could have had the
  pipeline created in a business the token does not own. Both are covered by
  "cannot re-point a provisioned row at another business", which fails if
  either check is removed.
- **Audit** (`modules/ops/audit.ts`): every call an ordinary `audit_log` row —
  actor = the token's owner, `payload.via = "ops_token:<prefix>"`,
  `batch_id`, `row_id`.
- **Bootstrap + skill**: `npm run create-ops-token <superadmin-email> <label>`
  prints one token with the two env lines; `skills/vendercrm-ops/` documents
  the flow, the limits and the "stop the row, ask the owner" rule.
- **Tests**: `ops.isolation.test.ts` (pre-existing tenant/site/pipeline/key
  all 404, another token's batch/rows 404, allowlist unlocks only
  site-create, site born inactive, revoked/expired resolve to nothing);
  `ops.integration.test.ts` (all five steps repeat without duplicating,
  public ingest still 403s on the inactive site, failures stored verbatim and
  re-runnable, audit payload carries `via` + `batch_id`).

## Decisions and deviations

1. **`createSite` gained an optional `isActive`** (default true, unchanged
   for every existing caller) rather than ops creating the site and
   deactivating it. §18.1.4 says born inactive; a create-then-update would
   leave a window, however short, in which the site accepted leads.
2. **The site's auto-issued "inicial" key is revoked by the site step.** Its
   plaintext goes nowhere in this path, and leaving it live would both strand
   an unrecoverable credential and spend one of the site's two rotation slots.
3. **A repeated key step returns `api_key: null`**, not a second key. There
   is no stored plaintext to return, and re-issuing would silently consume
   the rotation slot for a key nobody asked for.
4. **`apiError`'s code union gained `conflict`** (409) for a taken slug or a
   site already holding two keys — §18.3 asks for 409s, and the existing
   union had no honest code for one.
5. **An admin e-mail that already belongs to a user is a 422**, not an
   adoption: that account may be a member of another business, which an ops
   token may not reach into.
6. **`OPS_TEST_PHONE`** was added to `lib/config/env.ts` (default
   `+595981000000`) and `.env.example`, per §18.3's "phone from settings".
7. **`src/modules/ops/**` joins the raw-`db` eslint exemption list**, with the
   reason stated there: four tables with no tenant column for `tenantDb` to
   scope, plus the pre-context token lookup.
8. **A pre-auth per-IP limit (300/min) sits in front of the token lookup**, so
   an unauthenticated caller cannot spend unbounded database reads; the
   per-token limit (120/min) is §18.1.8's.
9. **The console reads take no context argument** (`listOpsTokens()`,
   `listAllOpsBatches()`, …), the way `listTenants()` doesn't — their only
   callers are behind `requireSuperadminContext()`.

## Known issues

- **Explicit `stages` are created verbatim, with no won/lost marking** — a
  custom stage set has no "Ganado" stage flagged `is_won` until someone edits
  it in the CRM. Omitting `stages` uses the default set, which is flagged.
  Guessing which of a session's stage names means "won" was not worth it.
- **`reset_email_sent: false` wherever Resend is unconfigured** (dev, CI, a
  fresh deploy). The tenant and admin exist; the admin needs a reset link
  from the superadmin console until mail is configured.
- **Nothing deletes.** A half-provisioned row is finished, corrected or left
  alone; there is no ops endpoint that removes a tenant, site or key, and
  cleanup is the owner's from the CRM.
- **Every ops site leaves one revoked `site_api_keys` row** (decision 2) —
  visible on the site's key list as a revoked key nobody issued by hand.
- **Token creation, revocation and the allowlist have no UI until O2** —
  `npm run create-ops-token` is the only way in, and it cannot set an
  allowlist or an expiry (the page will).
- **Rows are not deletable and batches never auto-close**; `setBatchStatus`
  exists for O2 to call.

## Verification

`npm run check:migrations`, `npm run lint`, `npm run typecheck`,
`npm run build` green; `npm test` green at **1076 passing, 0 failing** with a
local MySQL (the two AI-driver suites need CI's `AI_DRIVER=openai` env to run
rather than skip). Scripted end-to-end run against the dev DB over HTTP,
documented here so it can be repeated: `npx tsx scripts/create-superadmin.ts
<email> <password> <name>` → `npm run create-ops-token <email> "dev run"` →
`npm start` → `POST /api/ops/v1/batches` → `POST …/batches/{id}/rows` → the
five `POST /api/ops/v1/rows/{id}/{tenant,site,pipeline,key,test-lead}` calls
twice each: 201 then 200 with the same ids, one site (inactive, defaults and
tag set), one pipeline, one active key, one contact + deal, seven
`ops_objects` rows and six audit rows carrying `via` and `batch_id`. A second
token gets 404 on that batch and row; a wrong token gets 401; the site's own
key gets `403 Site is inactive` from `/api/v1/leads`.
