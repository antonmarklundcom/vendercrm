Sonnet, wave 2 lane 2, phase 4 of the sequential `sonnet-wave2-lane2.md` run.
Branch `phase/p16` off `main` at `0f29f9d` (P15 + its index line).

## Built

- **`companies` table** (`db/schema/crm.ts`, migration `0037`): tenant-scoped
  `name/ruc/phone/email/address/notes/custom`, a unique `(tenant_id, name)`
  index (same "no two companies with the same name" posture contacts already
  have on phone), and a nullable `contacts.company_id` + index — a contact is
  never required to have a company.
- **`modules/crm/companies.ts`**: CRUD (`createCompany`/`updateCompany`,
  `CompanyNameTakenError` on a duplicate name), `getCompany`, `listCompanies`
  (each row gets `contactCount`/`openDealCount`, computed in Node over the
  tenant's own small contacts/deals tables — same precedent as
  `dashboard/summary.ts`), `listContactsForCompany`/`listDealsForCompany`,
  `setContactCompany` (the one-field pointer update a contact's own page
  uses), and `deleteCompany` (admin-gated by the caller, refuses while the
  company still has contacts — the §10 1S pattern applied to a company).
- **`modules/crm/merge.ts`**: `mergeContacts(ctx, winnerId, loserId,
  fieldChoices?)` in one transaction. `contactReferenceColumns()` walks every
  table in the schema via `is(value, MySqlTable)`/`getTableColumns` to find
  every `contactId` column generically, rather than hand-listing tables that
  would silently go stale as new ones are added; each gets one re-pointing
  UPDATE. `contact_tags` is special-cased (unions the loser's non-duplicate
  tags onto the winner, since `(contactId, tagId)` is unique). `custom` JSON
  unions with the winner winning key conflicts; earliest `createdAt` and
  first-touch attribution are kept; an explicit field choice wins, otherwise
  the winner's non-empty value does. Writes a `contact.merge` audit log with
  the full per-table row counts and the field choices made.
- **`modules/crm/duplicates.ts`**: `findDuplicateCandidates` — pairwise
  matches on normalized email and on `normalized name + first-6-digits of
  phone`, deduped so a pair is never reported twice.
- **UI**: `/companies` (list with contact/open-deal counts + create form),
  `/companies/[id]` (contacts, deals, edit form, admin-gated delete —
  disabled while it still has contacts); a company picker and a "fusionar"
  tab on `/contacts/[id]` (admin-only merge dialog, per-field winner/loser
  radios); a "posibles duplicados" panel on `/contacts` linking straight into
  the merge dialog with the second contact pre-selected
  (`?otherId=`). Added `/companies` to the CRM nav group.
- **`app.contacts.tabs.contratos`** was missing from all three locale files
  since P13 added the tab in code without ever adding its label — fixed here
  alongside the new `fusionar` tab label.

## Decisions and deviations

1. **Merge re-points columns generically, not via a hand-written table
   list.** `contactReferenceColumns()` is schema-introspection (same idea as
   `restore-check.ts`'s `schemaTableNames`) so a future table with a
   `contactId` column is re-pointed automatically instead of silently being
   missed by a merge. The integration test asserts this list actually
   contains today's known tables, so a schema change that removes one is
   still caught.
2. **`deleteCompany` doesn't gate on admin itself.** Like the existing
   `deletion.ts` functions, admin-gating is the caller's job
   (`requireTenantAdmin()` in the server action) — a service function takes
   whatever `ctx` it's given rather than assuming a role.
3. **Company counts are computed in Node, not SQL.** Same precedent as
   `dashboard/summary.ts`: a tenant's companies/contacts/deals are all small
   tables, and a plain read-and-reduce is simpler than a join per row.
4. **Duplicate detection is pairwise, not clustering.** A tenant with three
   near-identical contacts sees three pairs, not one three-way group — matches
   how the merge dialog works (always exactly two contacts), and avoids the
   complexity of transitive grouping for a first pass.

## Known issues

- No bulk "merge all found duplicates" action — each pair is reviewed and
  merged one at a time via the dialog, deliberately, since merges aren't
  reversible.
- The duplicates panel re-scans every contact on every `/contacts` page load;
  fine at today's per-tenant contact volumes, worth caching if a tenant's
  contact count grows large enough to make the O(n²) pairwise comparison
  noticeable.
