Phase rules:
- `web-push` library; VAPID keys from env (`WEB_PUSH_PUBLIC_KEY`,
  `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_SUBJECT`), documented in `.env.example`,
  generated by a `scripts/generate-vapid.ts`; absent keys = feature hidden, never
  a crash (same pattern as Resend and Sentry).
- Table `push_subscriptions` (tenant, user, endpoint unique, keys, user_agent,
  created_at, last_seen_at, failed_at). Route `POST/DELETE /api/push/subscribe`.
- Service worker `public/sw.js`: push → showNotification with the url; click →
  focus or open. No offline caching in this pass. Register from the app layout
  only when signed in; an "Activar notificaciones" control in settings and a
  one-time banner on the inbox for mobile.
- Job kind `push.send` (tenant, user, payload) drained by the worker; 410/404 from
  the push service deletes the subscription. Enqueue on: inbound WhatsApp
  message (assigned user, else every active user in the tenant, capped to one
  push per conversation per 2 min), conversation assigned, task due (from the
  existing reminder chain), every `notifications` row P1 writes.
- Users can mute per kind in settings (`users.push_prefs` json).
- Tests: subscription lifecycle, fan-out rules, 410 cleanup. Manual check on an
  Android Chrome installed PWA is a §4.4 human step: write it in the PR body.
- Re-runnable; minor issues → docs/log/p2.md.

Exit: with keys set, a `push.send` job for a fake subscription reaches the
`web-push` call in tests; without keys, nothing renders and nothing throws;
settings toggle persists; lint/typecheck/test/build green; PR merged.
